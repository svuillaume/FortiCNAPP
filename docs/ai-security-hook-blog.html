Autonomous Patching: To Be or Not to Be

The hidden risk of pre-commit security hooks in AI coding assistants — and why the "safer" mode might not be safer.

2026-06-04 ~10 min read FortiCNAPP Code Security v1.7.1
SV
Sam Vuillaume
Consulting Systems Expert, Cloud & AI Security · Fortinet · June 4, 2026 · ~10 min read · Field · PreSales · Architecture

AI coding assistants like Claude Code now write entire features, refactor modules, and ship code at a pace no security team was sized for. Security hooks were the industry's answer: scan before you commit, block the bad stuff, keep vulnerabilities out of your codebase.

The pitch makes sense. But there's a design decision buried in most implementations that deserves far more scrutiny: what happens after the block?

The answer, in most tools, is that the AI decides — and acts — without asking you.

TL;DR

Pre-commit security hooks in AI tools can silently grant the AI permission to auto-fix, auto-suppress, or skip CVEs — with no human in the loop.

Post-task mode is the safer default: findings surface as a report, humans decide what to fix.

Know which mode your tools are running in. It's one JSON field. Check it today.

How the Hook System Works

Modern AI coding tools support a hook system that lets plugins intercept tool calls before they execute. The Code Security plugin registers a PreToolUse hook, watches for git commit commands, scans staged files for IaC and SCA findings, and denies the commit if Critical or High severity issues are detected.

So far, so good. The problem is what comes next.

When a hook blocks an action, it returns a permissionDecisionReason — a message fed directly back to the AI explaining why the action was blocked. Here's what that message actually looks like, straight from the plugin source:

# From pre-commit-scan.sh, lines 307–325

MESSAGE="Fortinet Code Security scanned your staged files
 and detected ${STAGED_CRIT} Critical, ${STAGED_HIGH} High
 security issues. The commit has been blocked.

 What would you like to do?
 1. Fix the issues - update the code to resolve the findings
 2. Add exceptions - suppress via .lacework/codesec.yaml
 3. Skip for now - leave findings as-is and continue"

The AI reads this, picks an option, and continues. No human confirmation required.

The Autonomous Remediator Problem

Option 1 — "Fix the issues" — sounds great on paper. In practice, it means the AI will attempt to patch CVEs, upgrade dependencies, or modify infrastructure code autonomously, without asking you first.

Critical Blind Dependency Upgrades

A CVE fix bumps lodash to the latest version. The latest version has a breaking API change. The scan passes. The app breaks in production.

High Suppression as a Fix

The AI adds an exception to .lacework/codesec.yaml. The finding disappears from future scans. The vulnerability stays in the code.

High Cascading Changes

A single CVE fix pulls in new transitive dependencies, each with their own risk surface — none scanned as part of the original staged files.

Critical False Confidence

The commit goes through clean. The scan passed. But the fix was cosmetic, incomplete, or introduced new issues the next scan won't catch until the next commit.

The Design Flaw

This isn't a bug — it's a design choice. The hook is intentionally structured to give the AI agency to remediate. The assumption is that autonomous fixing is a feature: developers shouldn't have to context-switch into security work mid-flow.

But there's a meaningful difference between:

Pre-Commit Mode

AI receives findings as a prompt and acts immediately — choosing to fix, suppress, or skip without human input.

Post-Task Mode

AI surfaces findings to a human who decides what to remediate, when, and how. Scans run after the task completes.

The first is a tool. The second is an autonomous agent operating on your codebase. Most teams haven't explicitly consented to the second.

Post-Task Mode: A Safer Default

In post-task mode, scans run after Claude finishes its task rather than gating a specific commit action. Findings surface as a structured report at the end of the task. The AI presents them. The human decides what to remediate, when, and how.

Security happens with the work, not to the work.

The tradeoff is timing: findings land after the work is done. But for most teams, that's the right tradeoff. Security remediation decisions should have a human in the loop — especially for Critical CVEs that touch dependencies or infrastructure.

Check your config

The plugin stores its mode in ~/.lacework/plugins/code-security.json. If you see "mode": "pre-commit", your AI is in autonomous-remediation territory. Switch to "mode": "post-task" to restore human review.

Four Questions to Ask Your Team

If your team is using AI coding tools with security plugins, run through this checklist:

  • 1
    What happens when a hook blocks an action? Is the denial reason fed back to the AI as a prompt? Does the AI act on it immediately?
  • 2
    Is there a human confirmation step before remediation? Or does the AI autonomously choose between fix, suppress, and skip?
  • 3
    Are AI-authored security fixes reviewed separately? A fix that passes a scan is not the same as a fix that is correct.
  • 4
    What is the default mode? Pre-commit feels safer but may be the more dangerous default for exactly the reasons above.

The Broader Point

The security community has spent decades arguing that controls should not be bypassable by the entity they are supposed to control. An AI that can both write code and remediate the security findings on that code — without human review — is effectively marking its own homework.

AI-assisted development is genuinely useful. AI-autonomous security remediation is a different thing entirely. And the line between them is blurring faster than most teams realize.

The core risk

When the AI that introduced a vulnerability is also the one that decides how to fix it, you've collapsed the check-and-balance that security reviews exist to provide.
